# v0.3 install=work validation

This is the Phase 7 (issue #132) checklist. v0.3.0 is **not** releasable
until every row in §"Coverage matrix" has a green check from a fresh-machine
run — no mock backend, no hand-edited config, no `inferdctl pull` precondition.
Run from the release tarball that the GitHub Actions release workflow
produced for the matching target triple, **not** from `cargo build`.

The procedure mirrors what an end user does:

1. Download the platform tarball from the release page.
2. Extract.
3. Run the platform install script (or the manual equivalent — both must work).
4. Verify the daemon picks the right runtime backend, pulls the configured
   generate + embed models, and answers a real prompt + a real embed.

If any step fails, **don't fix in place** — record the failure, file an
issue, and do not cut the release. The whole point of Phase 7 is to catch
shape gaps before users do.

## Coverage matrix

Tarballs ship from `.github/workflows/release.yml`. Every shipped target
must be exercised on hardware that can actually load the matching backend
MODULE; running the macOS-Metal flow on a 2018 Intel Mac doesn't validate
Metal, it validates the Metal-not-available CPU fallback.

| Platform     | Target triple                  | Accelerator probe expected | Hardware  | Owner       | Status |
|--------------|--------------------------------|----------------------------|-----------|-------------|--------|
| Linux x86_64 | `x86_64-unknown-linux-gnu`     | CPU                        | any       | Win Claude  | ☑ 2026-06-01 (rc.9, forced-CPU smoke: 68 layers on CPU, real gen) |
| Linux x86_64 | `x86_64-unknown-linux-gnu`     | CUDA                       | NVIDIA    | Win Claude  | ☑ 2026-06-01 (rc.8, clean install=work) |
| Linux x86_64 | `x86_64-unknown-linux-gnu`     | ROCm                       | AMD       | —           | skip   |
| Linux x86_64 | `x86_64-unknown-linux-gnu`     | Vulkan                     | any GPU   | —           | skip   |
| macOS arm64  | `aarch64-apple-darwin`         | Metal                      | Apple Si  | Mac Claude  | ☐      |
| macOS x86_64 | `x86_64-apple-darwin`          | CPU                        | Intel Mac | —           | skip   |
| Windows      | `x86_64-pc-windows-msvc`       | CPU                        | any       | Win Claude  | ☑ 2026-05-27 |
| Windows      | `x86_64-pc-windows-msvc`       | CUDA                       | NVIDIA    | —           | skip   |

Rows marked **skip** are not blockers for v0.3.0. They become blockers if
the release tarball claims to support that accelerator (e.g. if a future
release adds a CUDA-Windows wheel, that row must flip from skip to ☐).
Note that ROCm and Vulkan are exercised by CI's clippy+test on the
`dl-backends` feature path — only the install=work + real-inference loop
is gated here.

## Per-platform procedure

The flow is the same shape on all three platforms; only the install
mechanic differs. Each block ends with the same three checks:

1. `inferdctl doctor` reports the expected `accelerator=` and `device:`.
2. A real generate request answers (≥4 tokens, no `error` frame).
3. A real embed request returns vectors (no `error` frame).

### Windows (CPU)

```powershell
# 1. Extract the release tarball.
$tag = "v0.3.0"
$target = "x86_64-pc-windows-msvc"
$tarball = "inferd-$tag-$target.zip"
Expand-Archive -Path $tarball -DestinationPath C:\Dev\inferd-$tag

# 2. Install via the per-user script. -SourceBinary stages the binary
#    AND copies backends\*.dll next to it (per ADR 0019). No elevation.
cd C:\Dev\inferd-$tag\inferd-$tag-$target
powershell -ExecutionPolicy Bypass -File .\packaging\windows\install.ps1 `
    -SourceBinary .\inferd-daemon.exe

# 3. Wait for the auto-pull to finish (first boot only).
inferdctl watch

# 4. Verify backend pick.
inferdctl doctor
# expect:
#   backend         OK   llamacpp accelerator=cpu gpu_layers=0 v2=true ...
#   device          OK   <CPU model name> vram=0 B
# (no GPU device line on a CPU-only host)

# 5. Real generate.
inferdctl -p "Reply with exactly the word: pong"
# expect: a streamed response containing "pong", clean exit.

# 6. Real embed.
echo '{"id":"emb-test","input":["hello world"]}' | `
    inferdctl admin embed   # or use the embed pipe directly
```

### Linux (systemd --user, CPU)

```bash
# 1. Extract.
tag=v0.3.0
target=x86_64-unknown-linux-gnu
tar -xzf inferd-$tag-$target.tar.gz
cd inferd-$tag-$target

# 2. Install: copy daemon + backends/* into ~/.local/bin (RPATH=$ORIGIN
#    means libllama.so loads from there), drop the systemd unit.
mkdir -p ~/.local/bin
cp -f inferd-daemon ~/.local/bin/
cp -f backends/* ~/.local/bin/
mkdir -p ~/.config/systemd/user
cp -f packaging/inferd.service ~/.config/systemd/user/   # flattened in the tarball (no systemd/ subdir)
systemctl --user daemon-reload
systemctl --user enable --now inferd

# 3. Wait for auto-pull.
inferdctl watch

# 4–6. Same doctor / generate / embed as Windows. `accelerator=cpu`
# expected on a CPU-only host.
```

### Linux (CUDA)

Same as the CPU flow, on a host with the CUDA Toolkit + a working
`nvidia-smi`. The release tarball already ships `libggml-cuda.so` in
`backends/`. The probe should pick CUDA over CPU at first
`LlamaCpp::new`.

```bash
inferdctl doctor
# expect:
#   backend  OK   llamacpp accelerator=cuda gpu_layers=99 v2=true ...
#   device   OK   NVIDIA GeForce <model> vram=<N> GiB
```

If the probe still picks CPU on a known-good NVIDIA host, the failure
mode is usually:

- `libggml-cuda.so` missing from `~/.local/bin/` (verify
  `ls ~/.local/bin/libggml*`).
- CUDA driver mismatch (`ldd ~/.local/bin/libggml-cuda.so` reports
  unresolved symbols).
- `INFERD_FORCE_BACKEND=cpu` set in the systemd environment by mistake.

### macOS (Metal)

```bash
tag=v0.3.0
target=aarch64-apple-darwin
tar -xzf inferd-$tag-$target.tar.gz
cd inferd-$tag-$target

# install-launchagent.sh detects ./backends/ and flattens *.dylib next
# to inferd-daemon (RPATH=@loader_path resolves them). Refuses to write
# to /usr/local/bin/ if the user doesn't own it.
./packaging/launchd/install-launchagent.sh ./inferd-daemon

inferdctl watch
inferdctl doctor
# expect:
#   backend  OK   llamacpp accelerator=metal gpu_layers=99 v2=true ...
#   device   OK   Apple <chip> vram=<N> GiB
```

### macOS (Intel CPU fallback)

If anyone runs this — same flow, expect `accelerator=cpu` and no Metal
device line. Not a v0.3.0 release blocker (no Intel Mac tarball is
shipped today; the cross-compile is technically possible but is a
follow-up).

## Forced-backend smoke (one platform suffices)

The probe exposes `INFERD_FORCE_BACKEND` for benchmarking + sanity-
checking that a non-default MODULE actually loads. Run this on whichever
platform has the most accelerators present (typically Linux+CUDA box):

```bash
INFERD_FORCE_BACKEND=cpu inferd-daemon &  # or via systemctl edit
inferdctl doctor    # expect accelerator=cpu even on a GPU host
```

This step protects the operator escape hatch from regressing silently.
The previous v0.2.x compile-time pick had no equivalent and we lost
visibility every time someone forced CPU "for benchmarks" and then
forgot to undo it.

## Sign-off

Validation is **complete** for v0.3.0 when:

- All non-skip rows in the coverage matrix above are ☑.
- The forced-backend smoke ran clean on at least one platform.
- `CHANGELOG.md` Unreleased section names this doc and the date the
  validation completed.

After sign-off, Phase 8 (#133) ratifies ADR 0019 to *accepted*, updates
/site copy, and cuts the v0.3.0 stable tag.

## Findings log

Failures or near-failures hit during the runs above. Each gets a
short paragraph and a fix link. None of these are sign-off blockers
on their own; they are remediated in place and the row is re-run.

### 2026-05-27 — Windows CPU run

- **install.ps1 exited with code 36 even on a clean run.** Root
  cause: `sc.exe query inferd-daemon` returns 1060 when the legacy
  v0.2.1 SCM service is absent (the common case in v0.3+). PowerShell
  inherits `$LASTEXITCODE` as the script's own exit when no other
  native command runs after it; `1060 % 256 = 36`. Fix: capture the
  legacy-service detection result, then reset `$LASTEXITCODE` to 0
  so downstream packaging tooling reads the install as successful.
  Caught at line 107 of `packaging/windows/install.ps1`.
- **Embed pipe is single-frame, not stream + done.** The embed
  protocol terminates with a single `embeddings` (or `error`) frame
  per ADR 0017 — there is no separate `done`. Validation scripts
  that wait for `done` will time out. Doc-only, no code change.

### 2026-06-01 — Linux x86_64 CUDA run (rc.7, RTX 5080 / WSL Ubuntu)

Run against `inferd-v0.3.0-rc.7-x86_64-unknown-linux-gnu.tar.gz`
(sha256 verified) on WSL Ubuntu, RTX 5080 (driver 596.36, 16 GiB),
systemd `--user` as PID-1. **Verdict: rc.7 does NOT install=work on
Linux out of the box — release blocker.** Once the blocker is worked
around by hand, the full ADR 0019 CUDA path works end to end.

- **BLOCKER — release.yml bundled the glibc family into `backends/`.**
  The CUDA-bundling step's BFS copy loop staged `libc.so.6`,
  `libdl.so.2`, `libpthread.so.0`, `librt.so.1`, `libm.so.6`,
  `libstdc++.so.6`, `libgcc_s.so.1`, and `ld-linux-x86-64.so.2` next
  to `libggml-cuda.so`. Because `libggml-cuda.so` (and the daemon's
  `$ORIGIN/backends`) RUNPATH is `$ORIGIN`, the loader *prefers* the
  bundled (runner-built) glibc over the host's. The runner's glibc is
  not bit-identical to the consumer's, so the daemon dies immediately
  on boot:
  `symbol lookup error: .../libc.so.6: undefined symbol:
  __nptl_change_stack_perm, version GLIBC_PRIVATE`.
  A fresh user who follows the install steps verbatim gets a
  crash-looping unit, never reaching auto-pull. **Fix:** the copy loop
  now skips the glibc family via an `is_system_lib` predicate (same
  allowlist the final verification pass already used), so those libs
  resolve from the consumer's own glibc and are never staged. After
  deleting the eight wrongly-bundled libs by hand, the daemon boots,
  auto-pulls both models, and binds all sockets. `build.rs`
  `stage_backends_dir` was ruled out as a source — its `is_ours`
  filter only stages `ggml*`/`llama*` artefacts. Fix lands in
  `.github/workflows/release.yml`; needs a fresh rc to ship.
- **Probe correctly picks CUDA once the glibc mismatch is gone.**
  `runtime accelerator probe complete registered=[Cuda, Cpu]
  chosen="cuda"`, `ggml_cuda_init: found 1 CUDA device` (RTX 5080,
  cc 12.0, 16302 MiB), `offloaded 25/25 layers to GPU`,
  `inferdctl doctor` → `accelerator=cuda` + `device: CUDA0
  vram=15.9 GiB`. The skiplist works: `libcuda.so.1` /
  `libnvidia-ml.so.1` resolve from `/usr/lib/wsl/lib`, and the CUDA
  redist (`libcudart`/`libcublas`/`libcublasLt`) resolve from
  `backends/`.
- **Real generate + real embed both work on CUDA.** v1 UDS socket:
  multi-token stream terminating in a `done` frame
  (`backend=llamacpp`, token field is `content`). Embed UDS socket:
  single `embeddings` frame, 2 vectors × 768 dims,
  `model=embeddinggemma-300m`, `backend=llamacpp`.
- **DOC — systemd unit path was wrong in this checklist.** The install
  step said `cp packaging/systemd/inferd.service`, but the workflow
  flattens it to `packaging/inferd.service` in the tarball (the
  `systemd/` subdir is not preserved). Following the old step gives
  "No such file." Fixed in the Linux (CPU) install block above.
- **MINOR — `inferdctl doctor` prints `gpu_layers=0` even on CUDA.**
  The journal shows `offloaded 25/25 layers to GPU`, so the offload is
  real; the doctor line's `gpu_layers` field is cosmetic. Root cause:
  the default config ships `n_gpu_layers = -1` ("offload all") and
  `build_accelerator_info` does `(-1).max(0) = 0`, so "all" renders as
  0. Display-only; not a blocker. Worth mapping -1 → the actual layer
  count (or a literal "all") before v0.3.0 stable.

### 2026-06-01 — Linux x86_64 CUDA + CPU clean run (rc.8, RTX 5080 / WSL)

Re-ran from `inferd-v0.3.0-rc.8-x86_64-unknown-linux-gnu.tar.gz`
(sha256 verified) after a **full teardown** of the rc.7 install — no
manual lib deletion, install steps followed verbatim. **Verdict:
rc.8 IS install=work on Linux CUDA.**

- **glibc-bundling blocker is fixed.** The eight system libs are absent
  from the rc.8 `backends/` (verified by name); CUDA redist
  (`libcudart`/`libcublas`/`libcublasLt`) present. Daemon boots clean
  on first `systemctl --user enable --now` — no `GLIBC_PRIVATE` crash.
- **CUDA path end to end.** Probe `registered=[Cuda, Cpu]
  chosen="cuda"`, both models offloaded to GPU (gen 43/43, embed
  25/25), `doctor` → `accelerator=cuda device: CUDA0 vram=15.9 GiB`.
  Real generate ("Hello, how are you?", `backend=llamacpp`) and real
  embed (2×768, `backend=llamacpp`) both succeed.
- **BUG (pre-existing, fixed here) — `INFERD_FORCE_BACKEND=cpu` didn't
  actually run on CPU.** The forced-backend smoke on this GPU host
  logged `INFERD_FORCE_BACKEND override applied … kind=cpu` but the
  model still loaded onto CUDA0 (`llama_prepare_model_devices: using
  device CUDA0`). Root cause: `LlamaCpp::new` resolved the accelerator
  `kind` but passed the configured `n_gpu_layers` (default `-1` = all)
  to `load_model` regardless — llama.cpp only clamps to 0 when *no* GPU
  device is registered, not when the operator asked for CPU on a GPU
  box. Present since the ADR 0019 probe first landed (`7a8575e`), not
  an rc.8 regression. **Fixed** in `crates/inferd-engine/src/llamacpp/
  backend.rs`: when `kind == Cpu`, force `effective_gpu_layers = 0`
  before load, and report that through `build_accelerator_info`.
  Compiles + lints + unit-tests clean; the dl-backends runtime
  confirmation (forced CPU truly running on CPU on a GPU host) needs a
  fresh rc's CUDA CI build to verify on the box.

### 2026-06-01 — Linux x86_64 forced-CPU smoke (rc.9, RTX 5080 / WSL)

Re-ran the forced-backend smoke from the rc.9 tarball to verify the
`n_gpu_layers` gating fix on the box. **PASS** — the escape hatch now
genuinely runs inference on CPU.

- `INFERD_FORCE_BACKEND=cpu` on this GPU host: **all 68 model layers
  (43 gen + 25 embed) assigned to device CPU**, weights `CPU_Mapped`,
  zero layers on CUDA/GPU. Real generate succeeds (`backend=llamacpp`).
  On rc.8 these layers loaded onto CUDA0 — the fix works.
- **Residual (honest caveat, not a blocker):** llama.cpp still reserves
  a CUDA0 *compute scratch buffer* (~978 MiB) even at `n_gpu_layers=0`,
  because the CUDA backend stays registered in the ggml registry. The
  weights and per-layer compute are fully on CPU (the meaningful part
  for "force CPU for benchmarking"); the reserved scratch buffer is not
  used for layer math. Eliminating it entirely would require *not
  registering* the CUDA backend when CPU is forced — a deeper change
  than layer-gating, deferred. The line `prepare_model_devices: using
  device CUDA0` is device *enumeration*, not layer *placement*; the
  authoritative signal is the 68× `assigned to device CPU`.
