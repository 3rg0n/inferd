# v0.8 install=work + feature validation

Tracks the "releasable = install=work" gate for the v0.8 line: a
fresh-machine installer → `inferdctl doctor` reports `ready` → real
`generate` + real `embed` + the OpenAI-compat bridge, from a **release
archive** (no mock, no hand-edited config, no dev build, no "run pull
first").

What's new in 0.8.0 vs 0.7.0 (the surfaces this doc must exercise):

- **`tool_choice` enforced by grammar** (ADR 0029, issue #38) —
  `auto` / `required` / `none` as a constraint, not a hint.
- **`tool_choice_unsatisfied` on the `done` frame** (issue #62) — a
  `required` request that produced no call says so.
- **Breaking behaviour change** — a `tool_result` whose `tool_call_id`
  pairs with no `tool_use` in the same request is rejected with
  `invalid_request` instead of being attributed to a guessed tool.

> **Scope note.** These legs ran **before the `v0.8.0` tag exists**, from
> an archive staged locally with `packaging/stage-release.sh` off the
> release commit — not from a published, signed tarball. That is the one
> respect in which this differs from the v0.6/v0.7 legs, and it is why
> there is no SHA-256 / cosign verification row: there is nothing
> published to verify against yet. Everything downstream of extraction is
> identical to a real install, including running the installer at its real
> default paths.

## Feature gates — Windows x86_64 CUDA, 2026-08-10

Run against the installed daemon on `\\.\pipe\inferd` (generation) and
`\\.\pipe\inferd-infer-embed` (embeddings), spoken directly over the wire
by a ctypes named-pipe client rather than through `inferd-client`, so the
framing itself is exercised: `[uvarint payload_len][1 byte type][payload]`,
where `payload_len` counts the payload only (`frame.rs:83`).

### Baseline — the install=work claim

- **generate** — "reply with exactly: INSTALLWORK080" → `text` is
  `'INSTALLWORK080'` verbatim, `stop_reason=end_turn`, `backend=llamacpp`.
- **embed** — 256 dims (MRL truncation), **L2 = 1.000000**.
- **`inferdctl status`** — **exit 0**, three frames relayed with all
  fields. This confirms the #57 / #61 fixes live: `status` reads past
  every capabilities frame instead of stopping at the first.
- **`gpu_layers`** — `43` (E4B) and `25` (embed), i.e. the real offload
  count, confirming the #51 fix on real hardware rather than the clamped
  or over-asked number the previous code published.
- **`audio_sample_rate=16000`** on the audio-capable backend only; absent
  on the embed backend. Correct per ADR 0016 / ADR 0025.

### G-A — `tool_choice: "required"` produces a real call

Cooperative prompt ("What is the weather in Dublin?"), one declared tool:

```
tool_use: {"tool_call_id":"tc-1","name":"get_weather","input":{"city":"Dublin"}}
done:     stop_reason=tool_use, backend=llamacpp, input=68, output=14
```

### G-B — `tool_choice_unsatisfied` fires, adversarially

Prompt engineered against the constraint: *"Do not use any tools. Do not
call any function. Just reply with the single word: hi"*, `required`,
budget 64.

```
text: 'hi\n```\nhi\n```\n'
tool_use count: 0
done: stop_reason=max_tokens, tool_choice_unsatisfied=true
```

This is the measured behaviour ADR 0029 documents rather than a
regression, and it is the whole point of the flag: the grammar makes
*ending the turn* without a call unreachable (so the model cannot answer
in prose and stop), but unlimited non-call text is legal first, so a model
that disagrees with the prompt declines until the budget runs out — which
on its own is indistinguishable from ordinary truncation. The flag makes
it self-announcing, and therefore retryable. Note the degenerate
repetition, which is why raising the budget does not help.

### G-C — the breaking change, live

A `tool_result` citing an id that no `tool_use` in the request created:

```
error: code=invalid_request
message: render: messages[1].content[0]: tool_result references
         tool_call_id "call-that-never-happened", which matches no
         tool_use in this request
```

Rejected, naming the id. Previously this could reach the model attributed
to a guessed tool.

### G-D..G-F — the rejection surface

| Case | Result |
|---|---|
| `tool_choice` with no `tools` array | `invalid_request`: "tool_choice requires a non-empty tools array" |
| `tool_choice` + `response_format` together | `invalid_request`, mutual-exclusion message (only one grammar can be installed) |
| unknown `tool_choice` string | `invalid_request` |

### G-G — `none`, and that text stays reachable

`none` yielded 0 calls, and — the thing worth checking, since `none`
excludes the opener as *text* — prose remained reachable: "2 + 2" → `'4'`,
and a tool-seeking prompt answered in words. A control request with no
`tool_choice` at all made 1 call, so the gate is measuring the field and
not the prompt.

An earlier pass on a tool-seeking prompt returned `output_tokens: 0`,
which looked like `none` had masked everything. It had not: Tier-3
`none_still_answers_an_ordinary_question`
(`crates/inferd-engine/tests/tool_choice_llamacpp.rs:300`) asserts text
stays reachable, and the two follow-up prompts above confirmed it live.
Prompt-specific model behaviour, not a defect.

### G-H — the paired path still works

The non-breaking case, to confirm G-C did not over-reject: `user` →
`assistant`/`tool_use(tc-1)` → `user`/`tool_result(tc-1)` →
`'The weather in Dublin is sunny and 21°C.'`

### G7 — non-streaming responses dropped tool calls (found here, fixed)

**The one defect this leg found.** `stream: false` with a tool call
returned:

```json
{"choices":[{"finish_reason":"tool_calls","index":0,
  "message":{"content":"","role":"assistant"}}]}
```

`finish_reason` said a call had been made and there was no `tool_calls`
array to execute — so a non-streaming tool-using OpenAI SDK client could
not work at all. The identical request with `stream: true` was correct
throughout, which is why the SDK validation that cleared the bridge in
v0.6.0 missed it: that pass exercised streaming.

Cause: the two paths had diverged. Streaming built its terminal frame from
`ChunkBuilder::finalize`, while the non-streaming handler hand-wrote a
`serde_json::json!` body and discarded the builder it had been feeding
every frame (`let _ = builder;`). The tool calls were buffered and simply
never read. Pre-existing since the bridge shipped in v0.6.0 — deferred by
comment, not a v0.8.0 regression — but `tool_choice` is this release's
headline feature and this was its OpenAI-facing half.

Fixed by giving the non-streaming shape a typed home in
`inferd-openai-wire` (`ChatCompletion` / `CompletionChoice` /
`CompletionMessage`) and rendering **both** paths from the same buffer,
rather than copying the assembly into the second site. A regression test
asserts the two agree on the same generation.

After the fix, same request:

```json
{"object":"chat.completion","choices":[{"index":0,"message":{
  "role":"assistant","content":null,
  "tool_calls":[{"id":"tc-1","type":"function","function":{
    "name":"get_weather","arguments":"{\"city\":\"Dublin\"}"}}]},
  "finish_reason":"tool_calls"}],
 "usage":{"prompt_tokens":72,"completion_tokens":14,"total_tokens":86}}
```

Note `"content": null`, not `""` — OpenAI sends an explicit null on a
tool-call-only turn and clients branch on it.

**Round-trip proof**, which is the claim that actually matters to a
consumer: the `message` object above was posted back verbatim as
conversation history alongside a `role: "tool"` result, and the bridge
completed the loop → `'The weather in Dublin is sunny and 21°C.'` So a
caller can echo a returned choice into the next request unchanged, which
is what every OpenAI SDK's tool loop does.

Streaming re-verified unchanged after the fix (tool call present in the
terminal chunk, `finish_reason: "tool_calls"`, usage intact), and the
text-only non-streaming path re-verified for regression.

## Result — Windows x86_64 CUDA

Green, with one defect found and fixed rather than deferred. Every v0.8.0
surface was exercised against the installed daemon: the new `tool_choice`
enforcement including its adversarial case, the new
`tool_choice_unsatisfied` report, and the breaking `tool_result` rejection
together with the paired path it must not break.
