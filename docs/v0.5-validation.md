# v0.5.1 install=work + feature validation

v0.5.1 is **not** releasable until the gates below are green from a
fresh-machine run off the **release tarball** the GitHub Actions release
workflow produces (`.github/workflows/release.yml`) — never from `cargo
build`. No mock backend, no hand-edited config, no `inferdctl pull`
precondition.

The v0.5.1 line adds three things over v0.5.0 that this validation
exercises against a real model on real hardware:

1. **Gemma 4 GA thinking** — parser fix (`<|channel>thought` … `<channel|>`,
   not the old `<|think|>` … `<|/think|>`) **plus** the `RequestV2.thinking`
   activation field. The load-bearing proof: with `thinking=true` the
   reasoning trace lands on `thinking` response blocks and **no channel
   token leaks** into user-visible `text`.
2. **OCR image-token knob** — `mmproj_image_max_tokens` config field
   (#42) controls libmtmd's dynamic-resolution vision budget.
3. **Structured output (grammar)** — `response_format: json_schema`
   (carried from v0.5.0) still round-trips.

If any step fails, **don't fix in place** — record the failure, file an
issue, and do not cut the release.

## Feature gates (per platform, real model)

Run from a tiny Go harness built against `clients/go` that dials the
**live installed daemon** over the v2 LP wire (Windows named pipe /
Linux UDS) — no mock, no `cargo` test daemon.

### G1 — baseline text
Real `GenerateV2` text → coherent answer, terminal `done` with
`backend:"llamacpp"`.

- ☑ Windows x64 CUDA (2026-06-30): "capital of France" → `text="Paris"`,
  `stop=end_turn`, `backend=llamacpp`.
- ☑ Linux x64 CUDA / WSL (2026-06-30): same, `text="Paris"`.

### G2 — thinking activation, no channel-token leak (the v0.5.1 headline)
`thinking=true` → non-empty `thinking` block; user-visible `text`
contains **none** of `<|channel>`, `<channel|>`, `thought`, `<|think|>`,
`<|/think|>`.

- ☑ Windows x64 CUDA (2026-06-30): "6 times 7, reason briefly" →
  `thinking` block 552 chars ("Thinking Process: …"), final `text` =
  "**Reason:** … **Answer:** 42", **zero leak tokens**. `stop=end_turn`.
- ☑ Linux x64 CUDA / WSL (2026-06-30): byte-identical result, zero leak.

### G3 — structured output (grammar)
`response_format: json_schema` → output parses as the schema.

- ☑ Windows x64 CUDA (2026-06-30): schema {capital, population_millions}
  → `{"capital":"Paris","population_millions":2.1}`, valid per schema.
- ☑ Linux x64 CUDA / WSL (2026-06-30): byte-identical result.

### G4 — vision / OCR round-trip (raw-BLOB attachment, #42 knob)
Image sent as a raw-BLOB attachment (no base64) reaches mtmd; the
`mmproj_image_max_tokens` knob is wired into libmtmd's vision budget.

- ☑ Windows x64 CUDA (2026-06-30): 448×448 sparse-text PNG → RGB BLOB →
  `input_tokens=281`, answer recovered all 3 strings exactly
  ("INFERD-OCR / CODE: RX-5080 / STATUS: READY").
  **Knob plumbing proven**: setting `mmproj_image_max_tokens=1024`
  (ceiling above the natural ~250) keeps tokens at 281; setting it to
  `64` (below the model's vision floor) makes libmtmd reject the mmproj
  at load with a **clear** error (`image_max_pixels (147456) < image_min_pixels
  (580608)` → `mtmd_init_from_file returned null`) and the daemon exits
  1 — i.e. the value genuinely flows into mtmd init (a no-op knob would
  not change the pixel budget). See issue #47 for the background-mode
  log-visibility rough edge (non-blocker).
- ☑ Linux x64 CUDA / WSL (2026-06-30): same PNG → `input_tokens=281`,
  3/3 strings recovered.
