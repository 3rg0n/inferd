Tracks the "releasable = install=work" gate for the v0.6 line — v0.6.0 GA
below, then **v0.6.1** in its own section at the end: a fresh-machine
installer → `inferdctl doctor` reports `ready` → real `generate` + `embed`
+ the OpenAI-compat bridge, from the **release archive** (no mock, no
hand-edited config, no dev build).

What's new in 0.6.0 vs 0.5.1 (the surfaces this doc must exercise):
- vendored llama.cpp **b9850** + Gemma 4 **12B** support.
- **model auto-selection** (ADR 0023): total-VRAM-gated tier pick
  (≥ `model_autoselect_min_vram_gib`, default 20 → 12B, else E4B).
- **`inferd-http`** OpenAI-compat bridge (ADR 0020), now **with vision**
  (`image_url` → RGB attachment) — bundled in every tarball.
- Windows arm64 was **parked at the 0.6.0 tag** (task #185 — b9850 load
  crash). Fixed and un-parked in 0.6.1; see that section.

### G6 — structured output through the bridge (found broken, then fixed)
Initially the bridge **silently dropped** OpenAI `response_format`
(`ChatRequest` had no such field; `chat_request_to_v2` never set
`RequestV2.response_format`) — an OpenAI client requesting a JSON schema
got unconstrained text. **Fixed before rc.4**: added `response_format`
(+ `json_schema`) to `inferd-openai-wire` and mapped
`json_schema → RequestV2::JsonSchema{schema}` in the bridge (`text`/
`json_object` carry no schema → unconstrained, by design).
- ☑ Windows x64 CUDA (2026-07-13): OpenAI SDK `response_format`
  `{type:json_schema, json_schema:{schema:{capital,population_millions}}}`
  → `{"capital":"Paris","population_millions":67.7}` — valid JSON
  conforming to the schema, through the rebuilt bridge. Grammar now flows
  end-to-end via the OpenAI surface.
- ☑ macOS arm64 Metal (2026-07-13): same via the bundled `inferd-http` +
  OpenAI SDK — `image_url` data: URL vision → `"HELLO INFERD"` (exact
  transcription of the source PNG); `response_format` json_schema
  {capital, population_millions} →
  `{"capital": "Paris", "population_millions": 2.1458554836533653}` —
  valid, schema-conforming. Both bridge features (vision + grammar) green
  on Metal.

### Known bridge limitation — thinking not reachable via OpenAI surface
`thinking` is an explicit opt-in flag on the v2 wire
(`RequestV2.thinking=true`; omitted/false = no reasoning trace, verified
at `gemma4.rs`). OpenAI's Chat API has no standard "thinking" request
field, so a client **cannot activate thinking through the bridge** today
(native `inferd-client` consumers can). Documented, not a blocker — a
follow-up could map an OpenAI extension/param if wanted.

## v0.6.1 — post-GA review sweep re-validation

v0.6.1 is a post-GA correctness/security sweep: **F-1** per-request
attachment bounds (`MAX_ATTACHMENTS_PER_REQUEST` 32 /
`MAX_ATTACHMENT_BYTES_PER_REQUEST` 128 MiB), **F-17** bounded response
writes (`--write-timeout-secs`, default 60s), and two engine fixes on
the grammar/sampler path (double `llama_sampler_accept`, hoisted
vocab-sized candidate buffer). **No wire change** — `wire_version`
unmoved, v0.6.0 clients interoperate unchanged.

Release run `30735775875`: **8/8 jobs success** — SBOM, all five platform
legs (including the first successful `aarch64-pc-windows-msvc` release
leg — see the arm64 note below), and sign + publish. All archives,
`.sha256` files and cosign bundles are attached to the release.

**Caveat on that 8/8: the `Publish crates.io` job succeeded without
publishing anything.** `CARGO_REGISTRY_TOKEN` was not set on the repo, and
the job was written to no-op with a notice rather than fail the release — so
that green release run did **not** mean the library crates shipped. Worth
recording because the job list alone would mislead; check the registry API,
not the run summary. (That job no longer exists — see below.)

**Resolved the same day by a manual publish.** `inferd-proto` 0.6.1 and
`inferd-client` 0.6.1 are on crates.io, published from a working tree
verified byte-identical to the `v0.6.1` tag for both crate directories
(`git diff --stat v0.6.1 HEAD -- crates/inferd-proto crates/inferd-client`
empty). Registry API confirms `newest_version = max_stable_version = 0.6.1`,
not yanked, for both.

**The misleading job has since been deleted rather than given a secret.**
`release.yml` no longer has a `crates-io` job at all — a job that reports
success without doing the thing is worse than no job, and a permanent
registry version is a decision worth keeping in a human's hands.
Publishing is manual per `docs/RELEASING.md` §5 (rewritten with the real
two-crate procedure, the tag-identity check, and the registry
confirmation). So from the next tag on there is no crates.io job to
misread — but also nothing automatic: publishing is a step the releaser
must remember.

## Audio attachments — first live validation (post-0.6.1, task #199)

Audio had never run against a real model on any platform. Vision got that
treatment in #182; the audio path was **wire-complete and unproven** —
`Attachment::Audio::sample_rate` was read by nothing and the encoder's
required rate was never queried, so 44.1 kHz PCM fed to a 16 kHz encoder
was accepted and time-scaled ~2.75x into a fluent wrong answer (#198).
This is the gate that had to pass before README/site could advertise audio.

Platform: **Windows x86_64, CPU backend** (`dl-backends` build from
`main`; no CUDA lib staged in this dev build — irrelevant to a wire-contract
proof), Gemma 4 E4B + F16 mmproj. Harness: Go client over
`\\.\pipe\inferd-audio`, ground-truth speech synthesised with Windows SAPI
at 16 kHz mono and parsed to little-endian f32 PCM.

- ☑ **A — the encoder's required rate, read live.** `clip_model_loader: has
  audio encoder` on load, and the admin capabilities frame:
  `{"audio":true,"audio_sample_rate":16000,"backend":"gemma-4-e4b",…}`.
  First real evidence of the shipped mmproj's rate — #198's unit tests only
  *assumed* 16000.
- ☑ **B — matching rate accepted, model hears the audio.** 7.01 s / 112 240
  samples → 448 960 B f32 PCM BLOB at 16000 Hz → `input_tokens=199`,
  `stop=end_turn`, transcript **verbatim**: `"The quick brown fox jumps over
  the lazy dog. The secret pass phrase is tangerine harbor nine."` —
  **5/5** ground-truth phrases. This is content-level proof, not an
  `input_tokens > N` proxy.
- ☑ **C — mismatched rate rejected, both rates named.** Same PCM declared at
  44100 Hz → `code=invalid_request`, `audio attachment "a1": sample_rate
  44100 Hz does not match the model's audio encoder, which requires 16000
  Hz; resample before sending (the daemon does not resample)`.

**Defect found by running it:** neither client library could read the
contract the daemon advertises. `audio_sample_rate` was absent from both
`inferd_client::AdminEvent` and the Go `AdminEvent`, so no supported
consumer could see the rate it is required to honour — and Go had no
`AudioAttachment` constructor, so callers hand-built the struct and could
omit `SampleRate` entirely. Fixed in both clients (`audio_sample_rate`
field, `SupportsAudio`, `RequiredAudioSampleRate`, `AudioAttachment`) with
tests decoding the live frame above verbatim.

Not covered at the time: audio on any platform other than Windows x86_64,
audio on a GPU accelerator, and audio through the `inferd-http` bridge.
The bridge surface is now implemented and validated — next section.

## Audio through the inferd-http bridge (task #200, ADR 0025)

The daemon requires audio at exactly the rate its encoder advertises and
never resamples — so `input_audio` is only a real feature if the *bridge*
converts. ADR 0025 makes that the bridge's job (decode → downmix → resample,
rate read off the admin socket per request). This gate proves a client can
send audio at a rate the daemon would reject and still get a correct answer.

Platform: **Windows x86_64, CUDA** (RTX 5080; `target/release` daemon run
from the installed dir so the CUDA ggml DLLs resolve adjacently), Gemma 4
E4B + F16 mmproj, `audio_sample_rate=16000`. Client: **OpenAI Python SDK
2.45.0** — not curl. Source clip: Windows SAPI at **44 100 Hz stereo**
(2 640 566 B wav), i.e. both the wrong rate *and* the wrong channel count.

- ☑ **Transcription, non-streaming.** 44.1 kHz stereo wav → bridge decode +
  downmix + resample to 16 kHz mono → `input_tokens=397`,
  `finish_reason=stop`, transcript **verbatim**: `"Listen carefully. The
  access code is 4792. The color is magenta. The city is Reykjavik. The
  animal is otter. The number of boxes is 13."` — 5/5 ground-truth items
  (the model writes "13" for the spoken "thirteen"). Content-level proof.
- ☑ **Streaming (SSE).** "What is the access code?" → `'4792'` over 4
  deltas.
- ☑ **Multi-turn.** An audio user turn, an assistant turn, then a *text*
  follow-up ("Which city was mentioned?") → `'Reykjavik'`. The attachment
  stays bound to its own turn.
- ☑ **`format` is a hint only.** Real wav bytes labelled `"format":"mp3"`
  still decode (symphonia probes the container) → `4792`.
- ☑ **Undecodable payload → 400**, not 500 and not a hang: `audio content:
  audio decode failed: unsupported feature: core (probe): no suitable
  format reader found`.
- ☑ **Audio on a `system` message → 400**: `audio content is only allowed
  on \`user\` messages, not \`system\``.
- ☑ **Clip cap is exact.** 5 clips → 400 `too many audio clips in one
  request (max 4)`; 4 clips → 200. (Five copies of the *large* clip return
  413 from the 8 MiB inbound body limit instead — a correct, earlier bound,
  which is why the cap test uses a tiny clip.)
- ☑ **Text-only requests unaffected** and never dial the admin socket.

**Defect found by running it:** pointing the bridge at the **v0.6.1 GA
daemon** (which predates `audio_sample_rate`) produced `400 the daemon's
active backend does not accept audio input`. That is false — the backend
reported `audio:true`; it just advertised no rate — and it sent me auditing
the model instead of the daemon binary. The bridge now distinguishes
"no audio backend" from "audio backend, no advertised rate" and tells the
latter to upgrade the daemon, with five unit tests folding **verbatim live
caps frames** (audio+rate, audio-no-rate, embed-only) so the distinction
can't silently collapse again.

Not covered at the time: audio through the bridge on macOS/Linux, and audio
from a release **tarball** rather than a `cargo` build. **Both macOS and Linux
are now covered — the next two sections.** The tarball pass belongs to the
next tag.

## Bridge audio on Linux (task #200 follow-up)

The bridge's audio path had only ever run on Windows. Everything in it that
could plausibly be platform-sensitive is in the *decode* half — `symphonia`
container probing, the resampler, and the f32 PCM byte order that the wire
fixes as little-endian — so a second OS is the cheap way to find out whether
16 kHz mono LE-f32 was accidentally a Windows-shaped assumption.

Platform: **WSL2, Ubuntu 26.04 LTS, kernel 6.18.33.2-microsoft-standard-WSL2**,
built from `main` at `97ec186` (cargo 1.97.1, vendored llama.cpp `4f31eedb`),
`inferd-daemon` / `inferd-http` / `inferdctl` all `0.6.1`. Accelerator:
**`cpu`** — the RTX 5080 and `libcuda.so.1` are visible from WSL, but this
distro has no CUDA toolkit and no NVIDIA Vulkan ICD (only lvp / nouveau /
radeon / virtio), so the probe correctly lands on CPU. **This run is not GPU
coverage.** Daemon launched with the argv from
`packaging/systemd/inferd.service`; sockets came up with the documented modes
(`admin.sock` `srw-------`, `inferd.sock` / `infer.embed.sock` `srw-rw----`).

**Not from a tarball, deliberately.** The v0.6.1 release tarball's
`inferd-http` predates `input_audio` entirely, so there is no tarball that
*could* pass this gate. Built from `main`, which is what a Linux user tracking
`main` gets today; the tarball pass moves to the next tag.

Source clip: the **same** Windows SAPI recording used for the Windows bridge
gate — **44 100 Hz stereo**, 2 879 570 B, sha256
`52e0e4b711728717918431c5df7cde8e881efadd342cf0a6294da53825763aea`, header
re-parsed on the Linux side as `channels=2, rate=44100`. Wrong on *both* axes
and a rate the daemon rejects outright, so a pass can only mean the bridge
converted it. Script text reused verbatim from the #199 gate, so this is a
cross-platform comparison rather than a different test.

- ☑ **Transcription, non-streaming.** HTTP 200 in 11.1 s (CPU),
  `prompt_tokens=426`, `completion_tokens=37`, transcript **verbatim**:
  `"Listen carefully. The access code is 4792. The color is magenta. The city
  is Reykjavik. The animal is otter. The number of boxes is 13."` — 5/5
  ground-truth items ("13" for the spoken "thirteen" is the model's
  transcription choice, matched by the expect-string).
- ☑ **Streaming (SSE).** 37 deltas, `[DONE]` present, `4792` and `Reykjavik`
  both in the assembled text.
- ☑ **Edge cases 8/8**, same set as the Windows gate: format hint is a hint
  (mp3 label, wav bytes) → 200; undecodable audio → 400; audio on a `system`
  role → 400; 5 clips → 400 naming `max 4`; 4 clips at the cap → 200; 8 kHz
  **up**sampled → 200; 48 kHz stereo down-sampled + downmixed → 200;
  text-only unaffected → 200.
- ☑ **The bridge's resampling is load-bearing, proven by bypass.** The same
  clip's PCM sent *straight to the daemon* over the UDS at its true
  44 100 Hz (correct v2 framing: request frame, then the
  `{"type":"attachment_blob","attachment_id":"a1","len":2879524}` descriptor,
  then the BLOB) → `code=invalid_request`, `audio attachment "a1":
  sample_rate 44100 Hz does not match the model's audio encoder, which
  requires 16000 Hz; resample before sending (the daemon does not resample)`.
  Same clip, same daemon: rejected direct, correct through the bridge.

**Finding worth keeping — the daemon emits two capabilities frames, and the
first one says `audio: false`.** On this host the admin socket produced
`{"audio":false,"backend":"embeddinggemma-300m",…}` *first*, then
`{"audio":true,"audio_sample_rate":16000,"backend":"gemma-4-e4b",
"vision":true,…}`. So the non-latching `AudioSupport::fold` in the bridge is
load-bearing on real hardware, not a defensive nicety: a fold that latched on
the first frame would have disabled audio outright. Related: `inferdctl
status` shows one backend's capabilities even when two are registered, so
`status` alone cannot confirm audio support — dump the raw admin frames.

Still uncovered: bridge audio from a release **tarball** (impossible before
the next tag), and daemon or bridge audio on a non-Windows host with a **GPU**
accelerator — this Linux run was CPU and the macOS run was Metal-on-unified-
memory, so a discrete non-Windows GPU remains untested for audio.

**Cross-check with the macOS run above**, which was validated independently
the same day: three platforms, three OSes, two accelerator families, and
`audio_sample_rate=16000` reported identically by all three. That is the
contract holding across the axes it could plausibly have varied on. The one
platform difference worth noting is the capabilities-frame ordering finding
above, which is a per-host registration-order artefact rather than an OS
difference — it is the reason the bridge must not latch on the first frame,
whatever the platform.

### Defect found by step 4, and fixed

`inferdctl import` resolved its store with `match ConfigFile::load(..) { …
Err(_) => default_models_home() }`. The `Err(_)` swallowed **every** config
error, including validation failures — so a config the daemon rejects loudly
(`invalid config: backends list must not be empty …`) made `import` report
success while writing into `%LOCALAPPDATA%\models` instead of the
`models_home` the operator had specified. On an airgapped box that is a
successful-looking import into a store the daemon will never open.

Reproduced deliberately (config `{ "models_home": "<temp>/store",
"backends": [] }` → landed in the default store; same config with a real
backend block → honoured `models_home`), then fixed: the fallback now matches

### Two defects found, neither airgapped-specific

Both reproduce on a networked install and are therefore pre-existing, not
regressions in ADR 0028.

- **`inferdctl status` exits 1 on a healthy daemon, and reports the wrong
  backend's capabilities.** `cmd_status` reads *up to two* admin frames and
  looks for one whose `status != "capabilities"` to do the readiness check.
  But the daemon replays one `capabilities` frame **per backend** before the
  lifecycle snapshot, so on the default two-backend config (generation +
  embed) both reads are consumed by capabilities, the `ready` frame is never
  seen, and the fallback prints the *first* frame — the embed backend, which
  reports `v2: false, vision: false, audio: false`. `inferdctl watch` on the
  same daemon shows all three frames in order, confirming the daemon is
  correct and the client's read count is not. Reproduced with the v0.6.1
  networked CLI against the same daemon, so it is not new here. Any script
  gating on `inferdctl status` exit code fails against a healthy daemon.
- **`install.ps1` tells the operator to run `inferdctl`, then never installs
  it.** The installer stages `inferd-daemon.exe` and `backends\*` only. On an
  airgapped box its own closing message is `inferdctl import --name
  gemma-4-e4b <path.gguf>` — and `import` is the *only* way models get in —
  but `inferdctl` is not in the install dir, the install dir is not on `PATH`,
  and `Get-Command inferdctl` resolves nothing. The operator must find the CLI
  back in the unpacked archive. `install-launchagent.sh` has the same shape
  (it flattens `backends/` and stages the daemon; the CLI is not copied), so
  this is not Windows-only. Ships in both archives, but bites hardest on the
  airgapped one, where the instruction it prints is mandatory rather than
  optional.

### One new defect, plus both Windows defects confirmed cross-platform

- **NEW — the systemd unit cannot start on a fresh install (#59).** `systemctl
  --user enable --now inferd` fails `226/NAMESPACE` on a machine that has
  never run inferd: `Failed to set up mount namespacing:
  /home/<user>/.inferd: No such file or directory`. `ReadWritePaths=` carves
  `%h/.inferd` and `%h/.local/share/models` out of `ProtectHome=read-only`,
  and systemd resolves those during namespace setup. The unit has an
  `ExecStartPre=/usr/bin/mkdir -p` for exactly this, with a comment saying so
  — but `ExecStartPre` runs *inside* the namespace it is meant to make
  possible, so it cannot create the paths whose absence aborts setup. Proved
  by creating the two directories by hand and changing nothing else: the unit
  then started. `StartLimitBurst=3` turns it into
  `Start request repeated too quickly` within ~9 s. Fresh-install-only, which
  is why every prior Linux pass (all on boxes with a `~/.inferd` already)
  missed it.

  **Fixed 2026-08-07** by prefixing the command with `+`
  (`ExecStartPre=+/usr/bin/mkdir -p …`), which runs it outside the sandbox.
  Isolated first on stand-in units with no inferd in them (`ExecStart=/bin/true`)
  to pin the systemd semantics rather than infer them: on systemd 255 an absent
  leaf aborts `226/NAMESPACE` regardless of whether the parent exists; a present
  leaf passes; `ReadWritePaths=-<path>` avoids the abort but leaves the path
  unwritable, so it is not a fix; `+`-prefixed `ExecStartPre` succeeds and
  creates the directory. Then verified with the real unit and the shipped
  `inferd-v0.7.0-x86_64-unknown-linux-gnu` binaries from genuinely fresh state,
  running the pre-fix unit as a control in the same harness — unfixed: 3 ×
  `226/NAMESPACE`, neither directory created; fixed: 0 aborts, both created,
  unit `active`, first-boot `config.json` written, and all three sockets bound
  at the invariant-#6 modes (`srw-------` admin, `srw-rw----` gen + embed). A
  restart with the directories already present stays clean, so `mkdir -p` is
  still idempotent. Two extra probes confirm the sandbox was not simply widened:
  `$HOME` outside the carve-outs remains read-only to the unit, while
  `%h/.inferd` is writable from inside it.

  The `systemd-unit` CI job did install and start the real unit on a fresh
  runner, and stayed green throughout — because it never asserted the two
  `ReadWritePaths=` targets were *absent* first, so it could not tell a fresh
  install from a warm one. It now deletes both and asserts they are gone before
  starting, fails on `226/NAMESPACE` by name, and asserts afterwards that
  `ExecStartPre` created both and that the first-boot config landed.
- **#57 (`inferdctl status`) reproduces identically on Linux.** Against the
  live, healthy airgapped daemon: exit **1**, printing
  `"backend":"embeddinggemma-300m", "v2":false, "vision":false` — the embed
  backend. `inferdctl watch` on the same daemon shows all three frames
  (capabilities×2 then `ready`). Confirms the fixed-read-count diagnosis is
  platform-independent, not a Windows pipe artifact.

  **Fixed 2026-08-08.** `status` now reads until the lifecycle frame
  (bounded by 64 frames and the pre-existing 500 ms per-`recv` timeout) and
  prints *every* frame — one `capabilities` line per backend, then the
  lifecycle line. Printing all of them rather than selecting "the"
  generation backend is deliberate: ADR 0007 permits several generation
  backends, so selecting one would only relocate the arbitrary pick, and
  `doctor` already reports per backend. Verified live on Windows x86_64
  CUDA against the running two-backend daemon:

  ```
  {"accelerator":"cuda","audio":false,"backend":"embeddinggemma-300m","embed":true,...,"v2":true,"vision":false}
  {"accelerator":"cuda","audio":true,"backend":"gemma-4-e4b","embed":false,...,"v2":true,"vision":true}
  {"id":"admin","status":"ready","type":"status"}
  status exit=0
  ```

  Nine new unit tests cover the burst: the three-frame default, the
  single-backend case that made the bug latent, capabilities-only (not
  ready), a pre-`ready` snapshot, stopping at the snapshot instead of
  consuming live events, the frame bound, a stalled peer, an immediately
  closed socket, and frame ordering. They needed a
  `#[doc(hidden)] AdminClient::wrap_for_test` in `inferd-client` — the hatch
  `ClientV2` / `EmbedClient` / `RerankClient` already had and `AdminClient`
  alone lacked, which is why no test had ever driven this loop.
- **#58 (missing `inferdctl`) does not apply to Linux, for the reason that
  proves the point.** Linux has no installer to omit the CLI, and the
  README's documented `cp` line stages it explicitly. So the fix for #58 is
  to make the two scripted installers match what the Linux instructions
  already do.

  **Fixed 2026-08-08.** Windows stages `inferdctl.exe` next to the daemon in
  `%LOCALAPPDATA%\inferd` and appends that dir to the **user** `PATH`;
  `uninstall.ps1 -Purge` removes the entry. macOS stages nothing on purpose —
  `install-launchagent.sh` never relocates the daemon, so the extracted
  archive already *is* the install dir and already holds the CLI; the fix
  there is printing a resolvable invocation. Verified on Windows against a
  fake archive with all paths redirected to scratch and the live user `PATH`
  snapshotted/restored:

  | case | result |
  |---|---|
  | archive with CLI | `inferdctl.exe` staged; user `PATH` grew by exactly `len(installDir)+1`; backends staged |
  | re-run | `PATH` byte-identical; exactly **1** occurrence of the entry; no second "Adding …" line |
  | archive without CLI | `CLI: NOT INSTALLED`, warning emitted, commands printed as `.\inferdctl.exe`, nothing staged |
  | `REG_EXPAND_SZ` `PATH` | install **and** uninstall both decline: value kind still `ExpandString`, raw value byte-identical, `%USERPROFILE%` token intact, both warn, absolute path printed |
  | `uninstall -Purge` | entry removed, user `PATH` back to the original byte-for-byte, install dir deleted |

  Three traps, all now guarded in the scripts. `$env:PATH` is machine + user
  concatenated, so writing it to User scope doubles the user's `PATH`
  permanently (the code reads User scope specifically). `HKCU\Environment`'s
  `PATH` is practically capped near 2048 chars, so the append refuses past
  2000. And — found by review, then measured — if `PATH` is stored as
  `REG_EXPAND_SZ`, the .NET accessors cannot round-trip it: the getter
  returns the *expanded* string and the setter writes `REG_SZ`, so a naive
  append bakes today's expansion in and downgrades the value kind, silently
  destroying the user's `%VAR%` indirection. Measured directly on a planted
  `ExpandString` value: `%USERPROFILE%\bin;C:\lit` read back expanded, and
  the write came out `String`. Both scripts now detect the kind and decline
  rather than write; the install is still complete, since the closing message
  falls back to the fully-qualified path.

  One more, unrelated to #58 but worth recording: the harness lost the live
  `~/.inferd` because `uninstall.ps1 -Purge` deletes
  `$env:USERPROFILE\.inferd` unconditionally rather than deriving it from
  `-BinaryPath`, and `install.ps1` stops *any* running daemon regardless of
  target path. Correct for a real uninstall, hostile to a redirected test;
  the daemon rewrote the config on restart, and the CAS model store was
  untouched.

  **The macOS change is unverified on hardware** — no Mac on this box.
  `bash -n` passes; runtime coverage rides on the #60 macOS leg of #56.
- **`gpu_layers: 0` on a CUDA box.** Both capabilities frames report
  `gpu_layers: 0` while the daemon is demonstrably on CUDA (probe line,
  `ggml_cuda_init`, RTX 5080 detected, `n_gpu_layers: -1` in config). #51
  filed this as a macOS Metal reporting bug; it is not macOS-specific.

  **Fixed 2026-08-08** — the adapter clamped the configured `n_gpu_layers`
  with `.max(0)`, and llama.cpp reads a *negative* value as "offload all",

  opposite. It now resolves the negative form the way libllama does

  ```console
  {"accelerator":"cuda",...,"backend":"gemma-4-e4b","gpu_layers":43,...}

  [ ok ] backend: gemma-4-e4b accelerator=cuda gpu_layers=43 ...
  ```

  Each is the model's transformer-block count plus libllama's own `+ 1` for
  the output layer (Gemma 4 E4B 42 → 43, EmbeddingGemma 300M 24 → 25).
  Reporting-only — what is offloaded did not change. The reporter's separate
  *slow generation on Metal* claim is a distinct question and can only be
  settled on Mac hardware (#60).
