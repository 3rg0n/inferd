# v0.6.0 install=work + feature validation

Tracks the "releasable = install=work" gate for the v0.6.0 line: a
fresh-machine installer → `inferdctl doctor` reports `ready` → real
`generate` + `embed` + the OpenAI-compat bridge, from the **release
tarball** (no mock, no hand-edited config, no dev build).

What's new in 0.6.0 vs 0.5.1 (the surfaces this doc must exercise):
- vendored llama.cpp **b9850** + Gemma 4 **12B** support.
- **model auto-selection** (ADR 0023): total-VRAM-gated tier pick
  (≥ `model_autoselect_min_vram_gib`, default 20 → 12B, else E4B).
- **`inferd-http`** OpenAI-compat bridge (ADR 0020), now **with vision**
  (`image_url` → RGB attachment) — bundled in every tarball.
- Windows arm64 is **parked** this line (task #185 — b9850 load crash).

## Feature gates (per platform, real model, from the installed tarball)

Run against the installed daemon on `\\.\pipe\inferd` (Win) / UDS
(Linux) — no mock, no dev build, no `cargo` test daemon.

### G1 — baseline text

  `text="Paris"`. First request 65 s (one-time model load / CUDA warmup);
  warm requests instant.
- ☑ macOS arm64 Metal (2026-07-13): "capital of France, one word" →
  `text="Paris"`, `backend=llamacpp`, `stop_reason=end_turn`,
  `input_tokens=22`. Also `end_to_end_real_inference_over_uds`

### G2 — thinking activation, no channel-token leak
- ☑ Windows x64 CUDA (2026-07-12): "6×7, give the number", `thinking:true`,

### G3 — structured output (grammar)

### G4 — vision / OCR round-trip (raw-BLOB attachment)
- ☑ Windows x64 CUDA (2026-07-12): 768×420 known-text PNG → decoded to raw

### G5 — inferd-http bridge from the tarball (new in 0.6)
The bundled `inferd-http` launched against the installed daemon,
driven by the **real `openai` Python SDK** (base_url `/v1`):
- ☑ Windows x64 CUDA (2026-07-12): chat non-stream ("Paris"), chat stream
  ("Tokyo"), embeddings (768-dim), and **vision** (`image_url` data URL →
  transcribed TOPAZ-9021 + VALIDATED) — all pass. `/health` open, `/v1/*`
  served. Bridge is the tarball binary, not a dev build.
- ☑ Linux x64 CUDA / WSL (2026-07-12): same via the bundled Linux
  `inferd-http` (reached from the Windows-side SDK over WSL's localhost
  mirror) — chat, stream, embeddings (768), vision all pass.
- ☑ macOS arm64 Metal (2026-07-13): the tarball's `inferd-http` bound to
  `127.0.0.1:8090`, driven by the real `openai` Python SDK 2.45.0
  (base_url `/v1`): chat non-stream (`"Paris"`, `finish_reason=stop`),
  chat stream (`"1, 2, 3, 4, 5."`), embeddings float (768-dim) + base64
  (valid base64 string) — all pass.

### G6 — structured output through the bridge (found broken, then fixed)
Initially the bridge **silently dropped** OpenAI `response_format`
(`ChatRequest` had no such field; `chat_request_to_v2` never set
`RequestV2.response_format`) — an OpenAI client requesting a JSON schema
got unconstrained text. **Fixed before rc.4**: added `response_format`
(+ `json_schema`) to `inferd-openai-wire` and mapped
`json_schema → RequestV2::JsonSchema{schema}` in the bridge (`text`/
`json_object` carry no schema → unconstrained, by design).
- ☑ Windows x64 CUDA (2026-07-13): OpenAI SDK `response_format`
  `{type:json_schema, json_schema:{schema:{capital,population_millions}}}`
  → `{"capital":"Paris","population_millions":67.7}` — valid JSON
  conforming to the schema, through the rebuilt bridge. Grammar now flows
  end-to-end via the OpenAI surface.
- ☑ macOS arm64 Metal (2026-07-13): same via the bundled `inferd-http` +
  OpenAI SDK — `image_url` data: URL vision → `"HELLO INFERD"` (exact
  transcription of the source PNG); `response_format` json_schema
  {capital, population_millions} →
  `{"capital": "Paris", "population_millions": 2.1458554836533653}` —
  valid, schema-conforming. Both bridge features (vision + grammar) green
  on Metal.

### Known bridge limitation — thinking not reachable via OpenAI surface
`thinking` is an explicit opt-in flag on the v2 wire
(`RequestV2.thinking=true`; omitted/false = no reasoning trace, verified
at `gemma4.rs`). OpenAI's Chat API has no standard "thinking" request
field, so a client **cannot activate thinking through the bridge** today
(native `inferd-client` consumers can). Documented, not a blocker — a
follow-up could map an OpenAI extension/param if wanted.
